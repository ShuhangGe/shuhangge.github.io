## TL;DR — Today's Overview

> DeepSeek-V41-Flash loosens the system-prompt invariant, and OpenClaw's cloud workers grow a scheduler

1. **dsh 0.1.5-rc.1 and alpha.2: DeepSeek-V41-Flash becomes the default model and supports system-prompt updates inside conversation history without invalidating the KV cache; the sdk-minimal default tool surface changes again** The first line of the rc.1 notes (Sep 10): 'the DeepSeek model adapter adds DeepSeek-V41-Flash (deepseek-flash) with support for text, images and system prompt updates inside conversation history; new sessions default to this model', followed by yesterday's 'dynamic system prompt updates without invalidating the KV cache, when the model explicitly declares support'. Read together, the mechanism we flagged as unverified yesterday is mostly clear: it is not a harness trick. The V4.1 Flash model treats the system prompt as a message inside history, matching the V3 session format that 'folds the system prompt into message history'. For our production DeepSeek calls this means the cost model behind 'fixed tool surface plus byte-stable prefix' now forks by model. The DeepSeek API site published news260910 the same day; the title is opaque, but it is very likely the API announcement for V4.1 Flash, and pricing is unverified. alpha.2 (Sep 9) carries three more changes that bite: Web minimal and Python sdk-minimal now ship only a persistent shell by default with str_replace_editor opt-in; the Web plugin panel API changed (the conversation slot moved under main); and duplicate pagination cursors in MCP tool discovery are rejected. Two discussions were already reporting breakage on release day: #6119 cannot create a new conversation after updating, and #6105 says connection.rpc.handle() returns HTTP 405 from the browser on rc.1. — [source](https://github.com/deepseek-ai/deepseek-harness/releases/tag/dsh-v0.1.5-rc.1)

2. **Five OpenClaw cloud-worker PRs in one day: prepared image reuse (#143227), a bounded warm pool (#143372), an on-demand prepare RPC (#143838), survival across Gateway upgrades (#143858) and machine-spec projection (#143864)** #143227 (6,830 core lines across 45 files, merge-risk: compatibility and session-state) prepares admitted project content, authorized setup and the node runtime at their final paths before capturing the image, keeps separate pristine and completed manifests, and has a fresh dedicated node verify the completed tree and bind its workspace and HOME to exactly one session, with retirement preventing any other session from claiming the binding. #143372 (8,141 lines across 85 files): a successful session activation creates demand for one spare worker; assignment and placement happen atomically, each enrolled node can be consumed once, refill stays within the capacity limit, and expiry, restart and failed cleanup retain ownership until provider deletion is confirmed. #143838 adds the admin-only environments.prepare({ profileId, projectPath }) RPC that pins HEAD, reuses matching inventory or admits a build, and persists purpose in a nullable worker_environments.preparation_purpose column. #143858 (P1): a running cloud session used to fall back to provisioning and lose its machine after a Gateway update; it now stops the old runtime, revokes its credential, refreshes the worker bundle on the same machine and atomically updates both the environment and placement build receipts. This is a scheduler with a warm pool, leases and placement. Our knowledge-base line 'cloud workers only farm out exec and filesystem' has now been contradicted three days running. For us, the order of these five PRs (reuse images, then bound the warm pool, then pre-warm on demand, then survive upgrades) is an implementation roadmap for a multi-tenant worker pool and worth reading in full. — [source](https://github.com/openclaw/openclaw/pull/143372)

3. **Cloudflare Agents #2219 / #2223 / #2226: one Think turn used to read the whole transcript 2 + T times, about 10k billed row reads against 30 row writes for 400 messages and 20 tool updates** The #2219 body (1,744 core lines across 7 files) gives rare production-grade numbers: a long Think turn read the whole persisted history 2 + T times, where T is the number of tool updates in the turn (client results, approvals, cross-message results from server tools, execution outcomes); each read walks the sized path query (several billed rows per message for the byte subqueries) and hydrates every row. With a 400-message transcript and 20 tool updates that is on the order of 10k billed row reads for a turn whose stream log writes about 30 rows. All four fixes are on the read side: a tool update resolves its target row from memory and no longer calls session.getHistory(). #2223 derives the recovery progress marker from the stream log, removing one Durable Object KV get plus put per credited chunk (two per tool call, one per text segment start, one per five seconds). #2226: the auto-compaction threshold check ran the sized path CTE after every insert, so a turn's cost grew with the transcript; the total is now kept in memory and adjusted by delta. Yesterday we proposed 'design the schema by write count' as a new entry; today's evidence says the other half is bigger: Durable Objects bill reads as well as writes, and read amplification is invisible and grows linearly with session length. For us: any orchestration that re-reads the full history every turn needs its read bill computed first, whether the store is a Durable Object or Postgres. — [source](https://github.com/cloudflare/agents/pull/2219)

4. **OpenClaw #133693 (P1, diamond lobster): the flip side of generation fencing, isolated cron runs failed before model execution with 'prepared runtime generation was superseded', and a lease now pins the sampled generation** Yesterday's theme was 'give every mutable object a generation and compare-and-swap before writing'. Today shows where that same mechanism fails: the Gateway republished an agent's prepared runtime during asynchronous cron preparation, and by execution time the generation had changed, so the isolated cron run failed with 'prepared model runtime plugin generation was superseded'. The fix does not loosen the fence; it moves the check earlier. Cron samples the published reply-dispatch generation, validates owner identity, config and plugin-metadata identity, then acquires a lease pinned to that exact generation before auth or session persistence can publish a replacement, and holds that single generation through embedded execution. A later publication no longer drags an already-admitted run onto generation B, and 'selection facts from A with execution on B' cannot happen. Same day, #137147 adds the time dimension: a node.invoke timeout could expire early or late when the Gateway wall clock moved, and a positive remainder below one millisecond passed between owners could normalize to the existing unbounded-zero behavior; the whole chain now carries one deadline measured by elapsed time, and only the timeout sent to the node is rounded up. For us: a lease must pin both who and which generation, and deadlines must use a monotonic clock. Both belong in the task queue's defaults. — [source](https://github.com/openclaw/openclaw/pull/133693)

5. **OpenClaw #142754 (impact:security) plus #143198: two kinds of model-only, never-persisted injection, one forgeable and one that broke the prompt-prefix cache every turn** #142754 (open, needs-security-review and needs-product-decision): when no carrier message exists, prependRuntimeContextForModel() builds the runtime-context block as raw plain text inside a synthetic role: user turn instead of the structured, non-displayed carrier path. The agent sees it as conversation, an internal boundary leaks into user-facing chat, and because the delimiter constants can be byte-copied from the public npm package, any text of that shape is indistinguishable from a legitimate injection. #143198 (885 lines across 18 files, refs #142868 and #142869): every Gateway turn appended Git co-author attribution text to the user prompt whether or not the turn involved Git (a personal install logging office temperature through Home Assistant was told on every message that 'Git commit attribution for this turn has no additional Co-authored-by trailer'). Because that suffix was model-only and never persisted, the previous user turn changed shape on replay and invalidated prompt-prefix caches. The fix makes 'who to credit' session state rather than per-turn content. Together they are the counterexample to dsh's model-visible-iff-logged invariant: anything the model sees that is not on disk is either a forgery surface (#142754) or a cache killer (#143198). For us: runtime context reaches the model through structured fields, never through copyable text fences, and every byte the model sees must be in the log. — [source](https://github.com/openclaw/openclaw/issues/142754)

6. **Three Hermes tool_search changes: with a real install of 6 MCP servers and 311 deferred tools, every query returned 5 wrong tools (#106676); hosted connector tools now reachable through tool_search (#106842); a SHA-pinned plugin catalog (#69446)** #106676 is only 87 lines, but its data comes from a real install on main: tool_search used to fill every result list to limit (default 5) even when the only link between a result and the query was a common word such as 'email'. With one or two MCP servers this worked; with 6 servers and 311 deferred tools 'every search returned exactly limit names, and for queries the catalog could not answer, all of them were wrong'. It now returns nothing plus a retry hint when the query's most specific word matches no tool. Our knowledge-base line that hiding 19 tools behind tool_search saves about 6.5K tokens per call assumes retrieval is correct; at scale that assumption breaks first. #106842 (4,926 lines across 19 files, sweeper: risk-security-boundary): users signed in to the Nous Portal can find Gmail, Linear and Notion tools running on a Nous-hosted server through the same tool_search, and an unconnected account returns CONNECTION_REQUIRED with a sign-in link. This is a third shape of vendor-side connector: not the API-side MCP of OpenAI or Anthropic, but the harness's own hosted tool surface. #69446 (7,651 lines) makes a curated, SHA-pinned plugin catalog Hermes's single discovery system for out-of-tree plugins, with PR-gated admission CI and a requires_hermes manifest gate, and admits along the way that the earlier community index #64181 pointed at a canonical URL that 'never existed'. For us: once a tenant can attach hundreds of tools, retrieval quality and supply-chain admission are two faces of one problem. — [source](https://github.com/NousResearch/hermes-agent/pull/106676)

7. **OpenClaw #125977 (P1): an assistant turn that emitted partial text and then failed vanished from the next request; it is now replaced by a fixed marker 'this turn failed before it completed, do not redo its work without confirming'; #143592: the compaction engine kept touching a closed SQLite after timeout** #125977 (501 lines across 17 files, 20 comments, related #125942): an assistant response that emitted partial text and then errored or was aborted disappeared entirely from the next provider request, leaving the preceding user request and the next unrelated user request adjacent with no failed assistant turn between them. Both replay converters now replace the partial output with one fixed marker: [This turn failed before it completed. Do not redo its work without confirming with the user first.]. The decision uses the original content before model-specific thinking conversion, and empty, reasoning-only and no-content-placeholder failures get no marker. This sits with our rule that restored history is bracketed by system messages and an unanswered trailing user message must not be dropped, and adds a branch we had not written: a half-failed assistant turn must not be dropped either, and the marker must explicitly forbid the model from redoing the work on its own. #143592 (950 lines across 9 files): when a user compacted a session, the context engine kept working after a timeout, cancellation or early result and hit closed-database errors; the prepared runtime now lives until the actual compaction and cleanup settle, the watchdog observes the original invocation, and returning from the timeout race no longer ends physical resource ownership. This is the September sample of our 'compaction is rewritten almost monthly' entry, and this time the rewrite is about ownership lifetime rather than the algorithm. — [source](https://github.com/openclaw/openclaw/pull/125977)

8. **Two more OpenClaw upgrade-path failures: #143310 (P1) lost authentication for every provider after upgrading when an empty SQLite auth store sat beside a legacy auth-profiles.json; #142522, a dangling index left by the v15 to v16 migration kept doctor --fix from reaching its repair path** #143310 (2,490 lines across 31 files, 19 comments, fixes #143173): a legacy file holding only Anthropic credentials could block unrelated LiteLLM chat. The fix makes the migration diagnostic read provider metadata without importing legacy credentials; only recognized credential layouts narrow the refusal, while malformed JSON, metadata-only objects and unknown entries keep the owner-wide refusal, and affected providers get the provider list plus openclaw doctor --fix. #142522: the Skill Workshop v15 to v16 migration removed the workspace_dir column but left the idx_skill_workshop_collection_reviews_workspace_time index behind, so SQLite rejected schema inspection with 'no such column', and because write-admission and lease inspection run before canonical-index repair, doctor --fix reported a lease failure without ever reaching the repair path. Both share a root with yesterday's #141451 (read-only admission before the migration lease): when the migration tool's own self-check runs in the wrong order, the repair tool cannot repair the damage it caused. For our compose cluster: a migration's health check must pass in a half-broken schema state, otherwise doctor is just a second process that crashes. — [source](https://github.com/openclaw/openclaw/pull/143310)

## The Pattern

Today's strongest signal comes from the DeepSeek side, and it changes our cost model directly. dsh 0.1.5-rc.1 makes **DeepSeek-V41-Flash** the default for new sessions, and one sentence in the notes connects it to yesterday's puzzle: the model 'supports text, images and system prompt updates inside conversation history'. So 'dynamic system prompt updates without invalidating the KV cache' is not a harness trick that moves the system prompt somewhere else; the model accepts a system message inside conversation history and caches it as an ordinary prefix continuation. Two knowledge-base claims, that all three harnesses treat a byte-stable system prompt as an invariant and that any prompt change invalidates from the first affected token, now fork by model: V4 Pro, Hermes and OpenClaw keep the old rule, V4.1 Flash follows the new one. For our production agent this deserves an immediate experiment: swap the system prompt mid-conversation and compare prompt_cache_hit_tokens between V4 Flash and V4.1 Flash. The DeepSeek API site published news260910 the same day; the title is opaque and whether pricing changed with the new model is unverified.

The second signal is OpenClaw's cloud workers growing into a scheduler in five PRs on one day: prepared image reuse, a bounded warm pool, an on-demand prepare RPC, survival across Gateway upgrades, and machine-spec projection. One sentence from #143372 can go straight into our design doc: 'assignment and placement happen atomically, each enrolled node can be consumed once, refill stays within the capacity limit, and expiry, restart and failed cleanup retain ownership until provider deletion is confirmed'. That is the same problem as our multi-tenant cluster, and OpenClaw answered it with 8,141 core lines. The claim that 'cloud workers only farm out exec and filesystem' has been contradicted by three batches of evidence in three days and should be superseded.

The third signal is a pair of hidden bills. Cloudflare Agents #2219 gives production scale: one Think turn read the whole transcript 2 + T times, about 10k billed row reads against 30 row writes for 400 messages and 20 tool updates, whereas yesterday we only counted writes. OpenClaw #133693 is the flip side of yesterday's generation-fencing theme: a fence that is too strict kills legitimate in-flight work, and the fix is a lease pinned to the sampled generation rather than a re-check at execution time. Read together: every 're-read to confirm nothing changed' in the orchestration layer has a cost. Either put it on the bill, or use a lease to make it happen once.
