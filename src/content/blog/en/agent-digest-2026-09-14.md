## TL;DR — Today's Overview

> The gate is the thing that fails: an approved command can still launch as something else, and a verbose reviewer hands the decision back to a human

1. **OpenClaw #146517: a command could still start after its approval was revoked, and shell startup customization could substitute a different implementation for the reviewed command; the committed authorization now travels through preparation and native launch to the process boundary** Size XL, agents label, related to #103900. The two defects it names have the same shape: the approval holds at the decision point and does not hold at the execution point. The fix carries the committed authorization through asynchronous preparation and native launch, including delayed Claude execution and the PTY fallback, so Gateway and node commands honour approval-file revocation all the way to process launch; reviewed commands keep glob and tilde expansion but execute the bound programs, no longer via a shell path that can be rewritten. Policy stops at the actual launch boundary, and an already-started command is not killed by a later revocation. This lands directly on our code-layer evidence gate. Our judgment-high-risk-tool-two-phase-confirm-in-code (asserted 2026-09-08) says the preview-confirm gate belongs in the tool's own code, which quietly assumes the decision point is the execution point. #146517 shows three stages in between — preparation, expansion, shell startup customization — and each one can make the thing reviewed and the thing run be different things. Two companions the same day: #144587 raises the approval reviewer's completion budget to a bounded 1,024-token default, clamped down to the selected model's advertised maximum output, because a reviewer writing a thorough rationale for a complex command exceeds the budget and fails closed to human approval with risk=unknown, producing approval fatigue and defeating tools.exec.mode "auto" entirely; #147192 then lets the reviewer be configured with its own thinking effort (minimal, low, medium, high, xhigh, max) and fastMode, and fixes the shared simple-completion option builder dropping service-tier options before they reach the provider payload. Together: a model-driven gate fails in two directions — deciding too late (#146517) and saying too much (#144587) — and the second one looks like failing safe while functionally meaning there is no gate. — [source](https://github.com/openclaw/openclaw/pull/146517)

The setup-inference probe launches with preparedModelRuntimeMode "isolated-read-only", the hook does not participate, and the placeholder address is dialled as if it were real. The reporter classifies it himself as reliability, silent and self-inflicted load, and it carries the full clawsweeper set of labels: needs-maintainer-review, needs-product-decision, needs-security-review, needs-live-repro. Why it matters to us: our judgment-multi-tenant-requires-per-tenant-process asserts that isolation via hooks or a filtering layer does not hold, and until today that was an assertion. #146593 is its concrete mechanism — the hook is not written wrongly, the system simply has a code path that does not pass through hooks (probes, health checks, warm-up, catalog discovery), and that path bypasses the extension point precisely under the banner of isolated read-only. If our tenant routing lives in a hook or middleware, then every system-initiated call — readiness probes, model inventory refresh, scheduled work — has to separately prove it goes through the same routing, or the default will actually go out on the wire. This is the same line as judgment-tenant-param-no-default-runtime-gate: a placeholder is dangerous exactly because it is a default that something can take seriously. — [source](https://github.com/openclaw/openclaw/issues/146593)

3. **MCP SEP-2640, the Skills Extension, reaches final: a skill:// resource convention with archive distribution, extension id io.modelcontextprotocol/skills, alongside Python, C# and Go SDK PRs and host prototypes in gemini-cli, fast-agent, goose, codex and Claude Code** Labelled SEP, final and extension, with 35 comments, produced by the Skills Over MCP Working Group, transporting the design from experimental-ext-skills#69 with archive distribution per #83; reference implementations include TypeScript SDK wrappers and python-sdk#3485, csharp-sdk#1856 and go-sdk#1238. Two things to weigh. First, it rides the resources primitive, not tools. Our fact-mcp-hosted-connectors-tools-only records that the OpenAI Responses API and the Anthropic MCP connector support only the tools primitive over remote HTTP, which means vendor-hosted connectors cannot currently consume skills at all; the consumers are hosts that implement resources themselves, and the five prototypes the SEP names are all local hosts, which corroborates that entry rather than contradicting it. Second, it moves 'where a skill comes from' out of a locally installed directory and into an archive served by a remote server. For a cluster like ours that wants tenants to install skills, this SEP going final means the trust boundary has to be explicitly relocated to 'which MCP servers' skill resources may enter a prompt', and that list has to be read next to the ecosystem's auth posture: fact-mcp-ecosystem-auth-compliance-2026-08 records that only 35 to 38 percent of registry remote endpoints publish RFC 9728 metadata. — [source](https://github.com/modelcontextprotocol/modelcontextprotocol/pull/2640)

4. **OpenClaw #147206 (4,998 core lines across 43 files, merge-risk: compatibility): a parent agent can now keep a child's result internal — completionTarget "parent" stops completion delivery from publishing raw child output, and the parent may take the result, start another child, and stay silent** Fixes #27445, eight comments, proof telegram-e2e. The original problem states itself: a parent that chose NO_REPLY could still have the completion path publish the child's raw output — that is, the visibility of a child result did not belong to the parent, it belonged to the delivery path. Native one-shot spawns can now opt in explicitly: the parent receives the result, may start another child, and may remain silent with no automatic channel delivery and no fallback; an omitted target keeps existing behaviour; ACP, collected, visible, threaded, persistent-session and explicitly quiet spawns reject the option with actionable help; parent-session tool arguments and child-session transcripts stay visible to their own operator. There is no new config or default surface and no schema or protocol version bump. The same day, #112623 (54 comments) covers the opposite direction: parent turns used to miss retained completed-child results when the recent-history window expired, another child generation existed, or spawning was unavailable, while the previous revision loaded every retained result on every turn; now bounded outstanding child results come from the existing registry and SQLite completion records into parent runtime facts, discovery does not require spawn capability, and it explicitly does not acknowledge results or retry delivery. For us the pair splits a child result into three independent things: produced, discovered by the parent, and delivered to the user. Our judgment-large-results-bypass-coordinator only covers 'large results bypass the coordinator into storage, return a 1–2K summary', and says nothing about who decides whether it is user-visible. Under multi-tenancy that is not a formatting question: a child's raw output landing straight in a tenant's channel bypasses whatever redaction and safety re-check the parent layer performs (judgment-inter-agent-messages-are-untrusted-input). The delivery target has to be an explicit spawn-time parameter, never a default of the delivery layer. — [source](https://github.com/openclaw/openclaw/pull/147206)

5. **OpenClaw moves session history off the Gateway event loop wholesale: #147363 (3,846 lines across 56 files, merge-risk: availability) trades cold reads of 424–477 ms against 10–34 ms locally and about 270 MiB more warm whole-process RSS; #147491 then makes cold reads 7–20% faster with 15–19% less CPU** This is the group most likely to be skimmed past as performance work and the one that bears most directly on our cost model. #147363 states the problem: loading large or concurrent session-history pages occupies the Gateway event loop with SQLite reads and display preparation, delaying other requests. Afterwards, equivalent queued requests share work and later reads take fresh snapshots — at three explicitly measured costs: cold history reads of 424 to 477 ms against 10 to 34 ms locally, recurrence after the existing 60-second worker idle retirement, and about 270 MiB more warm whole-process RSS, with small-page tail latency able to increase. #140897 (7,566 lines across 58 files, carrying both compatibility and availability merge-risk labels) is the cleanup side of the same route: session cleanup used to repeatedly start Workers and decode metadata for unrelated sessions, and now reuses bounded Workers whose retained reclamation Worker retires after 60 idle seconds or explicit drainage, while openly accepting that source-runtime measurements show higher immediate process RSS. #147491 concedes it is a cold-start improvement, that warm performance is roughly unchanged, and that total process-tree RSS is not guaranteed to fall. #146770 attacks the same surface from the other side by requesting only required neighbours and keeping cursor pages consistent during concurrent history changes, and #146373 turns blocking skill-executable checks at agent startup into asynchronous preparation with four workers per preparation. Read together these five are a structural turn: the sentence in fact-openclaw-architecture-2026-09 about one long-running Gateway owning all session state with runtime state entirely in SQLite is becoming, in implementation, one Gateway plus a pool of bounded worker processes retiring after 60 idle seconds. For our compose deployment there are two directly transferable numbers: moving heavy SQLite reads off the main loop buys you a tenfold-plus cold-read latency and a few hundred megabytes of resident memory, plus an idle-retirement period you have to tune. That arithmetic belongs before the container sizing decision, not after the RSS fails to match in production. — [source](https://github.com/openclaw/openclaw/pull/147363)

6. **OpenClaw #147277 (P1): the migration lease has a five-minute TTL and a one-minute heartbeat, but the renewal timer only started after database admission finished — on large-state installations a slow startup exhausts a lease it already holds, and the Gateway refuses to start** A size-S fix whose mechanism is worth copying into our own lease implementation. ensureStartupMigrationLease acquired the lease first and then ran database readiness checks; when those checks took longer than five minutes the lease had already expired, and startup failed with a lost migration lease and restarted. The change is one sentence: start the existing renewal timer as soon as the lease is acquired, so the admitted reread finishes under a live lease. Our judgment-one-external-account-one-serial-lane already says lease preemption uses a single atomic SQL statement and the heartbeat runs on its own thread. The separate-thread half is right, but it does not say when the heartbeat starts beating. In our task queue, every path that grabs a lease and then does preparation of uncertain duration — pulling an image, connecting a database, warming a model — needs checking for whether renewal is scheduled after that preparation. — [source](https://github.com/openclaw/openclaw/pull/147277)

8. **OpenClaw #146601 (open, impact:security and impact:session-state): a core MEMORY.md is quarantined because its artifact provenance is untrusted — the stored hash matches, the file is a regular owned file under its bootstrap limit, and it still is not loaded; what is missing is a recovery path after human review, and the issue states plainly that inspection by an assistant does not count as owner approval** The real situation on 2026.9.3: a private agent's existing core memory is excluded from native bootstrap because its artifact provenance is untrusted, other eligible bootstrap files keep loading, and the quarantine is, as the reporter says, doing its job. 9. **OpenClaw #147154, feat(code-mode): pass results between code cells by handle — results.save, load and delete, at most 64 entries under a min(memoryLimitBytes, …) encoded-JSON allowance, with references carrying byte size, a sampled shape and a top-level count, expiring when the owning run or catalog closes and not surviving restarts** 743 core lines across 18 files, related to #147105. The problem is concrete: a Code Mode agent that needs an earlier cell's result in a later cell previously had to fetch the data again or copy it through model context. Now it can save JSON, inspect a small preview, and load a detached copy in later cells of the same run; the existing catalog owns the temporary result data, each code cell keeps its isolated VM, network-result provenance is preserved, and capacity failures leave existing references intact. This is a copyable implementation of our judgment-large-results-bypass-coordinator, and it supplies three boundary conditions that judgment never wrote down. Capacity: at most 64 entries under an encoded-JSON byte allowance, not an unbounded handle pool. What the summary should carry: byte size, a sampled shape and a top-level count — enough for the model to decide whether to expand it, at a predictable length. And lifetime: references expire when the owning run or catalog closes or changes, and explicitly do not survive restarts. That last one matters most for us. Our agents run under docker compose with a task queue, and 'does not survive restarts' means a handle is not a persistence mechanism; judgment-promised-intermediate-state-must-persist requires promised intermediate results to be written as a durable to-do first. The combined rule is that handles move data within one run, and anything that has to outlive a run or a restart needs its own persistence layer rather than a handle keeping it alive. — [source](https://github.com/openclaw/openclaw/pull/147154)

## The Pattern

Today has one axis, and the word is **gate** — not whether to have one, but the moment at which one stops working.

Three items point at that moment from three directions. **Deciding too late**: OpenClaw #146517 says a command's approval holds at the decision point and not at the launch point. A command could still start after its approval file was revoked, and shell startup customization could substitute a different implementation for the reviewed command. The fix carries the committed authorization through asynchronous preparation and native launch so that policy stops at the actual launch boundary. **Saying too much**: in #144587, the reviewer model writes a thorough rationale for a complex command, the output exceeds the review completion budget, and the gate fails closed to human approval with risk=unknown. It is failing safe, and for anyone running tools.exec.mode "auto" the effect is that automated approval stops working entirely and approval fatigue sets in. The fix raises the budget to a bounded 1,024-token default clamped down to the model's advertised maximum output, and #147192 then lets the reviewer carry its own thinking effort and fastMode. **Never reaching the gate at all**: in #146593, a before_model_resolve hook runs on interactive, cron and heartbeat turns, but the setup-inference system probe launches as isolated-read-only and never passes through hooks, so a deliberately placed placeholder baseUrl is dialled as if real and six model ids storm with UND_ERR_SOCKET retries. The reporter classifies it himself as silent, self-inflicted load.

For us these are not three bugs but three counterexamples to one rule: **a gate is correct exactly when the thing decided about and the thing executed are the same thing at the same instant.** Our judgment-high-risk-tool-two-phase-confirm-in-code says the preview-confirm gate lives in the tool's own code; judgment-gates-bind-to-real-consumption-point says a gate must run the real consumer's code path. Today adds a third sentence: a gate is itself a runtime component with a lifetime, a resource budget and a coverage area. It expires (#146517), it abstains when its own output overruns (#144587), and there are paths where it simply is not present (#146593). Our evidence-gate audit list should grow one check per failure: revoke and confirm the effect is immediate, drive the reviewer's output to its ceiling, and enumerate every system-initiated call path and prove individually that each one passes the gate.

The second axis is **ownership of child results**. #147206 turns 'is the child's output visible to the user' from a default of the delivery layer into an explicit spawn-time parameter, completionTarget "parent". #112623 goes the other way, letting a parent discover retained but unsettled child results. #147154 supplies three boundaries for handle-based result passing: at most 64 entries, references that carry byte size and a sampled shape, and no survival across restarts. Together they split a child result into three things — produced, discovered by the parent, delivered to the user. Under multi-tenancy that is a security question rather than a formatting one: a child's raw output landing straight in a tenant's channel bypasses every redaction and safety re-check the parent layer performs.

One item from the protocol side: MCP SEP-2640, the Skills Extension, is final, and skill:// rides **resources** rather than tools. Two consequences. Vendor-hosted connectors, which are tools-only, cannot consume skills today. And a skill's origin moves from a locally installed directory to an archive served by a remote server, which means the trust-at-install-time defence can no longer find the moment called install anywhere on the distribution path. Put next to the same day's #146601 — a quarantined MEMORY.md with no owner-review recovery path, and an explicit statement that inspection by an assistant does not count as owner approval — today's answer on trust boundaries is consistent: approval has to be a human action, explicit, and bound to the real execution point.

## Subagents and recovery

- [OpenClaw #146667 (P1, 1,050 core lines across 16 files): subagents stayed paused indefinitely after yielding while their own async tool results were already complete, and appeared as standalone sidebar sessions despite belonging to a parent](https://github.com/openclaw/openclaw/pull/146667) — The runtime now carries whether the current model response has earlier unobserved async tool results and defers the yield rather than claiming completion or ending the turn. This is a clean specimen of the 32.15 percent inter-agent misalignment bucket in fact-mast-multi-agent-failure-taxonomy: with no happens-before relation between yielding and results arriving, the child waits forever for an event that already happened. Every state in our queue that waits on an external callback deserves the same question — what if the result got there first.
- [OpenClaw #147209 (666 core lines across 20 files): lifecycle events, chat-history polling, parent-scoped session lookups and agent waiters repeatedly hydrated retained subagent task and result payloads, stalling the Gateway](https://github.com/openclaw/openclaw/pull/147209) — Child discovery, session-row projection and parent-scoped filtering now use the existing compact registry metadata cache, each filtered selection prepares its metadata once, and waiters share that cache to resolve stable collector IDs before loading on demand. It is the flip side of #112623: a parent must be able to discover retained child results, but discovery must not mean full hydration. For us: the subtask index and the subtask payload belong in two tables, and listing paths touch only the index.
- [OpenClaw #145057 (size XS): a turn interrupted by restart resumes with forceRestartSafeTools, the tool surface narrows to about nine read-only tools, and the model infers its permissions were revoked and asks the operator to 'restore write access' that was never taken away](https://github.com/openclaw/openclaw/pull/145057) — The restriction itself is correct — it prevents repeating a side effect whose outcome is unknown. What is wrong is a recovery prompt that says 'continue from the existing transcript' without mentioning that the tool surface was temporarily narrowed. This belongs with our judgment-history-restore-text-only-bracketed: when history is replayed, whatever changed in the environment since the model last looked has to be stated in the prompt, or the model will invent an explanation and act on it.
- [OpenClaw #141797 (1,526 core lines across 17 files, merge-risk compatibility, 32 comments): after a Gateway restart a recovered conversation gets a brief resumption notice in its original account and topic, and Telegram keeps typing visible while the recovered turn runs](https://github.com/openclaw/openclaw/pull/141797) — The self-limitation is the part worth keeping: main-session notices are live-only, while the existing subagent and terminal notices retain durable retries and deduplication, and both the notice and the typing activity revalidate their owner and current delivery policy at the platform-send boundary. Giving user-visible status and internal system state different durability guarantees is a reasonable split — as long as it is written down which layer is best-effort.

## Session state and write admission

- [OpenClaw #146842 (3,483 core lines across 38 files): embedded chat turns could write transcript repairs outside the agent database's write queue, or finish stream cleanup while an admitted repair still used their session resources](https://github.com/openclaw/openclaw/pull/146842) — The paths are prompt preparation, compaction recovery, cancellation and pending tool-result cleanup. The fix routes the remaining embedded transcript writes through the SessionManager admission owner introduced in #146732, rechecks live attempt authority after waiting, and awaits dependent repairs before publishing results. This is the edge-case list for our judgment-atomic-turn-write: a write queue is only a write queue when nothing bypasses it.
- [OpenClaw #146563 (1,919 core lines across 19 files): trajectory flushes could enter synchronous SQLite while a reclamation worker held its writer, blocking the Gateway thread needed to authorize that worker's commit; a failed append also discarded the buffered batch](https://github.com/openclaw/openclaw/pull/146563) — Three independent defects stacked: a deadlock where the authorizing thread is blocked by the thing it must authorize, data loss where a failed append drops the batch, and queued writes retargeting relative database or state paths when the working directory changed while they waited. Sharing the existing per-agent queue makes conflicting writes wait asynchronously, keeps failed batches available to retry, and pins queued operations to their original paths. - [OpenClaw #146246 (1,905 core lines across 27 files, merge-risk session-state, waiting on author): users who migrated a legacy multi-agent roster lost their identifiable default agent after restart, and `openclaw agents list --json` returned isDefault false for every agent](https://github.com/openclaw/openclaw/pull/146246) — It broke every integration that uses that field to select an agent, and the Control UI additionally treated an ownerless fallback row as the default while its Set Default action still wrote retired entry markers. A neighbour of judgment-security-default-tightening-needs-auto-migration: a mismatch between the field migration writes and the field readers expect is worse than not migrating, because it quietly returns an answer that is well-formed and wrong.
- [OpenClaw #145950 (1,901 core lines across 24 files): Gateway connection admission, request dispatch and cleanup were coupled to WebSocket-specific I/O, preventing another transport from safely reusing the authenticated lifecycle; they are now one transport-neutral owner](https://github.com/openclaw/openclaw/pull/145950) — The WebSocket adapter keeps receive, receiver limits, heartbeat, socket errors and physical liveness, and preserves the keepalive behaviour from #145191 including passing the underlying socket to startWebSocketKeepalive; it adds no endpoint, config, protocol or persistence surface. The 'WS control plane on 127.0.0.1:18789' in our fact-openclaw-architecture-2026-09 still holds, but the implicit premise that WS is the only transport is being dismantled, and the next release is worth watching.

## Security boundaries

- [OpenClaw #146356 (size S, merge-risk compatibility and message-delivery): the Nextcloud Talk webhook admitted an unbounded number of concurrent unauthenticated body reads, each incomplete request pinning a pre-auth reader for up to five seconds without ever consuming the authentication-failure budget](https://github.com/openclaw/openclaw/pull/146356) — Any client able to reach the listener could hold arbitrary numbers of sockets, request objects and timers, delaying or blocking legitimate webhook deliveries. The fix acquires a listener-owned in-flight slot before the unauthenticated read, rejects overflow with an immediate close-aware HTTP 429, releases the slot after signature verification and before authenticated dispatch, and serialises each connection's requests through the shared HTTP request lifecycle so an overflow rejection can never destroy a socket ahead of an earlier queued acknowledgement. The lesson in one line: an authentication-failure budget does not cover requests that have not failed yet, so the limit has to sit before the body read, not after authorization.
- [OpenClaw #147275 (5,090 core lines across 47 files): an agent can now drive the Gateway's own managed desktop through the `computer` tool without pairing a separate node on the same machine](https://github.com/openclaw/openclaw/pull/147275) — The Gateway supplies its managed display and private D-Bus session to a supervised helper; Gateway control requires explicit provider enablement and tool access, an explicitly enabled Gateway provider becomes the default when no target is supplied, and `target: "node"` retains paired-desktop selection. Note what changes shape here: 'the agent can drive a desktop' used to require a physical pairing action and is now a configuration switch, with the driven desktop sharing a host with the Gateway. In a multi-tenant deployment this provider has to be off by default and not tenant-togglable.
- [OpenClaw #145945, docs(skills): authorizing `gog` on a remote or headless Gateway could expose an OAuth callback through agent-visible input, lose remote-step state by changing config roots, and bypass host proxy policy after browser consent](https://github.com/openclaw/openclaw/pull/145945) — Only a size-XS documentation PR, but three rules worth copying: run the requested operation first and enter setup only after an authentication error; keep callback URLs out of chat and out of agent tool input, with the operator completing the manual paste or remote step two in a trusted Gateway shell; and preserve the resolved config context (GOG_CONFIG_DIR and the rest) across remote steps. 'Intermediate artifacts of a credential exchange must never appear on an agent-visible surface' should be a hard rule when we build tenant OAuth onboarding.
- [OpenClaw #147233 (open, impact:security): `view_image` rejects images inside an admitted task worktree — when the task working directory differs from the agent workspace, an absolute path is refused and a relative path resolves against the agent workspace instead](https://github.com/openclaw/openclaw/issues/147233) — The reproduction is specific: run an unsandboxed task in a managed worktree outside its agent workspace with `tools.fs.workspaceOnly: true`, create a small image inside that worktree with the coding tools, then call view_image with the absolute path. The source-level repro gives the exact createOpenClawTools({ workspaceDir, cwd, agentDir, ... }) combination. This is a specimen of a security check using the wrong base directory: once worktrees exist, workspaceOnly has two candidate meanings (the workspace or the cwd), and the tool picked one while the admission layer picked the other. Our worktree and sandbox path validation needs one authoritative definition rather than a per-tool judgment.

## Operations and startup

- [OpenClaw #143802 (size L): Doctor and Gateway restart readiness checks copied whole agent databases just to read schema metadata, with copy cost and temporary disk requirement growing with stored transcripts](https://github.com/openclaw/openclaw/pull/143802) — The previous revision bypassed the optimisation for configured agents — precisely the Doctor and restart callers that matter. Eligible schema checks now read version, shape and ownership metadata in one coherent read-only child transaction, while the parent still applies the existing ownership admission decision, isolating secondary agents and refusing default or system-agent mismatches. It complements #145577 and #145541 rather than replacing them. For us: readiness-check cost has to be decoupled from data size, or restarts get slower exactly as the data grows, which is when fast restarts matter most.
- [OpenClaw #146865 (size XS): when a stopped Linux Gateway still has child processes in its systemd cgroup, Doctor and update maintenance reported that service inspection was unavailable instead of naming the remaining tasks and the recovery action](https://github.com/openclaw/openclaw/pull/146865) — The typical case is a user service that cannot terminate a child owned by another account.
