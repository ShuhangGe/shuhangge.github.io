## TL;DR — 今日概览

> 闸门自己会失效：批过的命令仍能变形启动，审查器写太长就放行给人

1. **OpenClaw #146517：审批被撤销后命令仍能启动，且 shell 启动定制能把「已审查的命令」换成另一个实现；授权现在随准备与原生 launch 一起传到进程启动边界** size: XL，agents 标签，related #103900。自述的两个缺陷是同一个形状：审批在决策点成立，在执行点不成立。修法是把「已提交的授权」一路带过异步准备与原生 launch（含延迟 Claude 执行与 PTY 回退），让 Gateway 与 node 命令把审批文件的撤销一直尊重到进程启动；被审查的命令保留 glob 与 ~ 展开，但执行的是绑定的程序本身，不再经过可被改写的 shell 路径。策略停在真正的 launch 边界——已启动的命令不会被事后撤销杀掉。这条直接打在我们的代码层证据闸门上：我们的 judgment-high-risk-tool-two-phase-confirm-in-code（asserted_at 2026-09-08）写的是「两段式确认写在工具代码里」，它假定判定点就是执行点。#146517 说明中间还隔着准备、展开、shell 启动定制三段，每一段都能让「被审的东西」和「被跑的东西」不是同一个东西。配套两条同日：#144587 把审批审查器的补全预算从截断态提到 1,024 token 默认值（向下夹到所选模型的最大输出上限），因为审查模型给复杂命令写详细理由时会超预算、fail closed 成 risk=unknown 的人工审批，制造审批疲劳并让 tools.exec.mode: "auto" 形同虚设；#147192 再让 reviewer 独立配 thinking（minimal/low/medium/high/xhigh/max）与 fastMode，并修掉共享 simple-completion 选项构造器丢掉 service tier 的问题。三条合起来的结论：模型驱动的闸门有两个失效方向——判定太晚（#146517）和判定说太多（#144587），后者的表现是「安全地失效」但业务上等于没有闸门。 — [来源](https://github.com/openclaw/openclaw/pull/146517)

## 本期主轴

今天的主轴只有一个词：**闸门**。不是「要不要设闸」，是「设了闸之后它在哪一刻失效」。

三条证据从三个方向指向同一处。**判定太晚**：OpenClaw #146517 说，命令的审批在决策点成立、在启动点不成立——审批文件撤销之后命令还能起来，shell 启动定制还能把被审查的命令换成另一个实现。修法是把「已提交的授权」一路带过异步准备与原生 launch，让策略停在真正的 launch 边界。**判定说太多**：#144587 里，审查模型给复杂命令写详细理由，输出超过补全预算，闸门 fail closed 成 risk=unknown 的人工审批。它是「安全地失效」，但对开着 tools.exec.mode: "auto" 的用户，效果是自动审批全面失效加审批疲劳——修法是把预算提到 1,024 token 默认值并向下夹到模型的最大输出上限，#147192 再让 reviewer 独立配 thinking 与 fastMode。**根本没跑到闸门**：#146593 里，一个 before_model_resolve 钩子在交互、cron、心跳回合都跑，唯独 setup-inference 系统探针以 `isolated-read-only` 启动、不经过钩子，于是刻意留的占位 baseUrl 被当成真地址连出去，6 个 model id 一起 UND_ERR_SOCKET 重试风暴。报告者自己把它归为「静默的、自伤的负载」。

这三条对我们不是三个 bug，是一条规则的三个反例：**闸门的正确性等于「被判定的东西」和「被执行的东西」是同一个东西，在同一时刻。** 我们的 judgment-high-risk-tool-two-phase-confirm-in-code 写的是「两段式确认写在工具代码里」，judgment-gates-bind-to-real-consumption-point 写的是「闸门必须跑真实消费方的代码路径」。今天要加的第三句是：闸门自己是有生命周期、有资源预算、有覆盖范围的运行时组件——它会过期（#146517）、会因为自己的输出超额而弃权（#144587）、会有它压根不在的路径（#146593）。我们的证据闸门审计清单应该按这三条各加一行验证：撤销后立刻启动、审查器输出打到上限、以及枚举所有「系统发起」的调用路径并逐条证明它们也过闸。

第二条轴是**子结果的归属**。#147206 把「子的输出是否对用户可见」从投递层的默认行为变成 spawn 时的显式参数 `completionTarget: "parent"`，#112623 反过来让父能发现被保留但未结清的子结果，#147154 给出句柄式结果传递的三个边界（64 条上限、引用带字节数与采样形状、不跨重启）。合起来，子结果被拆成产生、被父发现、被投递三件事。在多租户下这是安全问题而非排版问题：子的原始输出直接落进租户频道，等于绕过父层的所有脱敏与安全回检。

协议侧一条：MCP SEP-2640 Skills Extension 进入 final，skill:// 走 **resources** 而不是 tools。两个后果——厂商托管连接器（tools-only）目前吃不到 skills；以及 skill 的来源从「本地装好的目录」变成「远端 server 发的归档」，「安装即受信」这条防线在分发路径上找不到那个叫「安装」的时刻了。配上同日 #146601（隔离的 MEMORY.md 没有人工复核恢复路径，且明确「助手看过内容不算所有者批准」），今天在信任边界上给出的答案很一致：批准必须是人做的、显式的、绑在真实执行点上的一次动作。

## 子 agent 与恢复

- [OpenClaw #146667（P1，1,050 核心行 / 16 文件）：子 agent 让出后无限期停住——它自己的异步工具结果已经完成，运行时却没在 yield 前观察到；侧栏里它们还显示成独立会话](https://github.com/openclaw/openclaw/pull/146667) — 修法是运行时携带「当前模型响应是否有更早的未观察异步工具结果」，有就推迟 yield，不在宣告完成或结束回合之前让出。这是 fact-mast-multi-agent-failure-taxonomy 里 32.15% 的「agent 间错位」的一个干净样本：让出与结果到达之间没有 happens-before 关系时，子会永远等一个已经发生的事件。我们的队列里凡有「等外部回调再继续」的状态，都要问同一句：结果先到了怎么办。

## 安全边界

- [OpenClaw #146356（size: S，merge-risk: compatibility + message-delivery）：Nextcloud Talk webhook 允许无限多个并发的未认证正文读取，每个未完成请求把一个 pre-auth reader 钉住最多五秒且从不消耗认证失败预算](https://github.com/openclaw/openclaw/pull/146356) — 任何能连到监听器的客户端都能占住任意数量的 socket、请求对象与定时器，从而延迟或阻断正常的 webhook 投递。修法：在未认证读取之前获取监听器拥有的在途槽位，溢出立刻回 HTTP 429 并感知连接关闭，签名校验之后、认证后分发之前释放槽位，并把每个连接的请求串行化过共享 HTTP 生命周期，保证溢出拒绝不会抢在更早的排队确认之前销毁 socket。教训一句话：**认证失败预算不覆盖「还没失败」的请求**——限流必须在读正文之前，不能在鉴权之后。
- [OpenClaw #147275（5,090 核心行 / 47 文件）：agent 现在能通过 `computer` 工具直接操作 Gateway 自己的受管桌面，不必在同一台机器上再配一个 node](https://github.com/openclaw/openclaw/pull/147275) — Gateway 把它的受管显示器与私有 D-Bus 会话交给一个受监督的 helper；需要显式启用 provider 与工具访问，显式启用后它在没给 target 时成为默认，用 `target: "node"` 保留配对桌面选择。注意这条改的是信任边界的形状：以前「agent 能操作桌面」需要一次物理配对动作，现在变成一个配置开关，而被操作的桌面和 Gateway 同宿主。多租户部署里这个 provider 必须默认关且不可由租户开启。
- [OpenClaw #145945 docs(skills)：在远端或无头 Gateway 上授权 `gog` 曾把 OAuth 回调经 agent 可见的输入暴露出来、改配置根就丢远端步骤状态、浏览器同意之后绕过宿主代理策略](https://github.com/openclaw/openclaw/pull/145945) — 虽然只是 size: XS 的文档 PR，但三条规则值得抄：先跑用户要的操作、只有在认证错误之后才进入 setup；回调 URL 不进聊天也不进 agent 工具输入，由 operator 在可信的 Gateway shell 里完成手工粘贴或远端第二步；跨远端步骤保留已解析的配置上下文（GOG_CONFIG_DIR 等）。「凭据交换的中间产物不得出现在 agent 可见面」应当是我们做租户 OAuth 接入时的硬规则。
- [OpenClaw #147233（open，impact:security，issue-rating 钻石龙虾）：`view_image` 在已准入的任务 worktree 里拒绝图片——任务工作目录与 agent workspace 不同时，绝对路径被拒、相对路径去 agent workspace 里解析](https://github.com/openclaw/openclaw/issues/147233) — 复现条件很具体：在 agent workspace 之外的受管 worktree 里跑一个非沙箱任务，`tools.fs.workspaceOnly: true`，用编码工具在该 worktree 里造一张小图，然后用绝对路径调 view_image。源码级复现给了 createOpenClawTools({ workspaceDir, cwd, agentDir, ... }) 的参数组合。这是个「安全检查用错了基准目录」的样本：workspaceOnly 的语义在引入 worktree 之后有两个候选答案（workspace 还是 cwd），代码选了一个、准入层选了另一个。我们的 worktree / 沙箱路径校验要有一处权威定义，不能每个工具自己判断。
