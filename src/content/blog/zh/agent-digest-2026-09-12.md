## 本期主轴

今天三个最强的信号来自三家不同的仓库，却在回答同一个问题：**长期状态归谁所有、什么时候可以换手**。

Cloudflare agents@0.23.0 的答案是「一次性换手，不回头」。ai-chat 0.12 在对象首次唤醒时把整张消息表导入线性 Sessions 链，全部导入才删旧表，回滚即空对话；think 0.18 把 withCachedPrompt() 变成空操作，因为「冻结的 prompt 现在总是持久化」。更值得记的是 #2193 对 facet 的重定位：它是隔离原语，不是「一个用户很多聊天」的建模方式。知识库里这条判断两周前还是我们的推断，今天是官方 changelog。

Hermes v0.21.2 的答案是「只允许一个写者，其余全部只读或走同一连接层」。四个根因没有一个是 SQLite 的错：profile 网关每 5 秒写根库、dashboard 启动即可写、cron 守卫裸 open() 取消 POSIX 锁、doctor 在活写者下 checkpoint。发布说明把裸 open() 叫「经典的 SQLite 损坏配方」。我们条目里的「热更新 WAL 损坏未解」建立在一份 RFC 上，而这批修复说明：结构问题的大头不在存储引擎，在旁路写者的纪律。

OpenClaw 的答案最贵：#144252 用 47,317 行只做「插件退役不打断在途工作」，#145172 把冷 transcript 搬进不可变 JSONL 但让 SQLite 保留身份，#144454 让 Crabbox 与静态 SSH 共用一套租约语义。三条加起来是同一个原则：换手之前先把 owner 钉住，钉不住就不换。

反面教材是 ADK 2.9.0：失败节点在 resume 时重跑而非重放，副作用会重复，changelog 直接要求「把节点体写成幂等的」。这不是 bug，是把责任推回给调用方。对我们的任务队列，这一天的结论很具体：每个有外部写的步骤必须有 {run_id}:{step_id} 幂等键；reset 要带 expectedSessionId；cron 要带 authProfileId；SQLite 旁路写者一个都不能有。Claude Code 两版里四处 prompt cache 修复讲的也是同一件事的另一面——重放形状一变，缓存就没了。
